# 一個畫面照著畫的規則

[English](interface.md) | [繁體中文](interface.zh-TW.md)

> 這個外觀不是品味。它是十條規則，而一個畫面是拿它們來判斷的，不是拿誰的意見。

Fediqo 用平台自己的控制項、平台自己的外框來畫。那是前提，不是偏好：系統畫出來的控制項，讀者早就會用、早就能用鍵盤到達、
早就聽得到它被念出來。留給我們的是它上面那一層 —— 用哪個圖示、隔多遠、一個顏色可以表示什麼、數字從哪裡來。這份文件就是
那一層，寫下來。

規則有編號，是為了讓一次審查可以指名其中一條。`S1` 與 `S8` 是畫面最常違反的兩條。

## S1 —— 圖示優先

一個動作就是一個圖示。它的文字活在 `help()`（給游標）與 accessibility label（給其他所有人）裡，不出現在畫面上它的旁邊。

一列一列的貼文，一次使用會被讀上百次，而它的動作每次都是同樣那六個。在每一個旁邊加上文字，就是每一列都要跳過的六個字，
而且第一屏之後眼睛早就不看了。

有兩種東西保留文字。一種是收不回來的 —— 靜音、封鎖、檢舉與刪除 —— 因為讀者需要被告知自己正要做什麼，而不是被提醒自己
早就知道的事。另一種是那個控制項本身就是唯一在說明讀者正在看什麼的東西：蓋住的貼文上那顆按鈕寫著**顯示**，因為模糊之上
的一隻眼睛是一個沒有慣例可以靠的圖示，而讀不懂它的人就無從知道被蓋住的是什麼。

| 這是什麼             | 怎麼畫                                       |
| -------------------- | -------------------------------------------- |
| 一般動作             | 只有圖示，配 `help()` 與 accessibility label |
| 破壞性或不可逆的     | 圖示，加上文字                               |
| 只有它在說明一個狀態 | 圖示，加上文字                               |
| 一個去處             | 圖示，有空間時加上文字                       |

## S2 —— 一個角色一個尺寸

互動圖示是 `Glyph.action`。可以按的東西至少是 `Hit.target` —— iOS 44、macOS 28 —— 而這個尺寸由 `IconButton` 決定，
不由每個呼叫端各自決定。

游標是瞄準，手指是覆蓋。這兩個數字是 Apple 的；自己挑一個的畫面，會剛好在其中一個平台上很難按 —— 而那種 bug 沒有人會回報。

## S3 —— 用間距分組，不用線

相關的控制項相隔 `Space.withinGroup`；群組之間至少是它的兩倍，而中間什麼都不畫。

群組之間畫線，畫出來的是三個盒子，但想要的是三口氣。眼睛自己會讀出一個空隙，而每一條線都是又一個記號，去跟那些真的有意義
的記號搶。

## S4 —— 顏色就是狀態

| 顏色            | 表示什麼               |
| --------------- | ---------------------- |
| 灰（secondary） | 靜止，什麼都還沒做     |
| 一個 tint       | 開著 —— 這是你做過的事 |
| 紅              | 這會拿走某個東西       |
| 橘              | 一台伺服器不太對勁     |
| accent          | 讀者在哪裡             |

沒有東西是為了好看才上色。分不出兩個色相的讀者，一樣拿得到每一個狀態，因為上面每一項同時也是實心或空心的圖示、一個字、
或一個位置。

## S5 —— 不發明數字

沒有任何伺服器告訴我們的數字就不畫。零表示沒有人，而它永遠不會畫在一則根本不知道的貼文上 —— 一列在計數存在之前就存進來的
資料什麼都不知道，在那裡畫 `0` 就是畫面在編。

開關也一樣：沒有人告訴我們的，畫成空心，而且不宣稱自己表示「沒有收藏」。

## S6 —— 一列有邊界，而且欄位對齊

沒有任何一列會為了裝下內容而長大。文字在固定的行數之後停住並帶一個刪節號，而那個刪節號就是這一列在說還有更多；只要有兩欄
的餘裕，附件欄就在那裡 —— 不論裡面有沒有東西。

那是幾行，跟著讀者的文字縮放走，永遠不是寫死的行數。在 13 點塞得下的行數，在 21 點會滿出來，而一列滿出來就是整個畫面上唯一
一列形狀不同的列。

**短的貼文不會被墊到跟長的一樣高。** 這條規則原本寫的是「每一列一樣高」，而這個 app 從來沒有做到過：把附件疊在文字下方的
那種排法一直都讓列貼合自己的內容，而那是每一支手機。讀者用來掃的是「每一列從同一個地方開始、在可預期的地方結束」——
那來自夾住文字的行數上限與保留的欄位，不是來自補高。把每一列都墊到最高的那一列，是拿大半個畫面去說沒有內容的話，而
[#79](https://github.com/cmj0121/fediqo/issues/79) 量過那個代價：五則貼文變成兩則。

## S7 —— 只用原生控制項

平台不畫的控制項是一個新的 issue，不是一次安靜的例外。如果一個畫面需要系統沒有對應物的東西，那是一個要攤開來吵的決定，
因為被花掉的是整個介面的前提。

## S8 —— 數字從 token 來

間距、圓角、字級與圖示尺寸都來自 `Theme.swift`。view 裡出現的裸數字是 bug。

寫在 view 裡的數字，是一個在別處改不動的數字。相隔一週寫下的兩個會不一致，而那個不一致在兩個畫面被並排之前都看不見。

| token       | 管什麼                                |
| ----------- | ------------------------------------- |
| `Space`     | 每一個間距與每一個 padding            |
| `Radius`    | 每一個圓角                            |
| `Glyph`     | 每一個符號尺寸                        |
| `TypeScale` | 每一個文字尺寸，一律經過 `fediqoFont` |
| `Hit`       | 值得按的東西的最小尺寸                |

文字用 `fediqoFont` 設定，不用 `.font(.system(size:))`，因為前者才會把讀者自己的文字尺寸帶下去 —— macOS 沒有給這棵樹
Dynamic Type。符號用 `fediqoSymbol`，而它不跟著縮放：一列的高度是從裡面的文字算出來的，會跟著文字長大的記號會撐破它。

這條規則禁止的是**沒有名字的**數字，不是數字。只屬於某一個 view、別處都用不到的量測值 —— 附件欄的寬度、composer 面板的
大小、rail 的兩個寬度 —— 就寫成那個 view 上一個有名字、有註解的 `static let`。等到第二個畫面也需要它，才搬進 `Size`。

## S9 —— 塞進被給的空間，不要去量它

一個 view 把自己的排法由寬到窄擺出來，取第一個裝得下的。它不去問自己有幾點寬，再從那個答案決定要畫什麼。

量出來的寬度是對某台裝置的猜測，`ViewThatFits` 是對這個視窗的回答。手機、Slide Over 裡的 iPad、正被拖窄的 Mac 視窗 ——
各自拿到自己撐得住的最寬那種排法；而還沒有人出貨的螢幕尺寸，是被構造出來地處理掉的，不是等 bug 被回報之後有人再補一個
數字。門檻還有第二個毛病：它不知道讀者的文字尺寸。560 點在 0.85× 是一列舒服的字，在 1.6× 是一列滿出來的字；而在 iOS 上，
這個 app 的縮放是去乘上手機本來就設定好的 Dynamic Type，不是取代它。

門檻只在排法表達不了那個選擇時才准用 —— 也就是一份清單的每一列必須得到*同一個*答案的時候，理由是 S6，而排法是一列一列
各自回答的。這種時候它要寫成一個具名的 `static let`，推導過程寫在旁邊，而且**其中屬於文字的那一份要乘上讀者的縮放**。
屬於圖片的那一份不乘：一張圖片在每一個文字尺寸下都是它本來的大小。

這條規則禁止的是一個知道自己有多寬的畫面。多一個畫面不是多一個 boolean，多一台裝置也不是多一個門檻。

## S10 —— 帶照片的一列是同一個高度

每一列只要帶照片，就跟其他帶照片的列一樣高。照片縮放到填滿那個框、放不下的裁掉，而被切掉夠多的時候，那一列
會說出來。

時間軸是一份讀者正在往下捲的清單。每一列高度都不一樣的清單，眼睛在每一則貼文都要重新找一次位置，而一張很高
的照片等於在決定它可以拿走讀者多少閱讀。所以卡片只有一個形狀 —— `AttachmentDeck.ratio` —— 不管照片本身是
什麼形狀。

**而且只有一個大小，挑成「有圖的一列幾乎等於沒圖的一列」。** 卡片跟 `PostRow.words` 一樣高，那是摘要被夾住的
高度：文字旁邊的照片，就跟文字被允許的高度一樣高。在 1280 點的時間軸量到 275 對 210；兩倍大的時候是 410 對
215。這也是「再縮就沒有用」的位置 —— 比它更矮，列高就由文字自己決定，照片縮小只換到一張更小的照片。

**縮放，絕不拉伸。** 照片保持自己的比例，放大到蓋滿卡片，超出的裁掉。被壓扁去配合框的照片就是另一張照片了，
而那是這裡唯一不允許的事。

**而被切掉的時候，那一列會說。** Mastodon 會送 `meta.original.width` 和 `height`，這個 app 有存下來，所以一列
知道自己沒顯示到什麼：低於 `AttachmentDeck.mostOfIt` 就出現一個標記說「還有更多」，而那個標記的意思是「打開
它」。高於它，被修掉的是照片的邊緣而不是照片的一部分 —— 3:2 的照片在這個卡片裡只少一絲，而每張照片都掛一個
標記，就是把雜訊放在事實該在的位置。會說出來這件事本來就是 S5 會要求的：一列顯示著某人照片的中間卻不說，就是
那一列在編造這張照片是什麼。

沒有照片的一列還是跟它的字一樣高。這條規則講的是帶照片的那些列；「一列是有界的而不是等高的」仍然是 S6 在說，
沒有任何東西會把兩行的貼文墊高到一張照片的高度。

這條規則禁止的是：一份在讀者底下移動的清單，以及一個畫面默默把別人照片的一部分當成全部。

## 當一條規則擋路

錯的規則就在這裡、公開地改，而那個修改在
[#35](https://github.com/cmj0121/fediqo/issues/35) 裡吵。安靜違反其中一條的畫面，是替所有人做了決定的畫面 ——
而那正是這十句話存在的目的。

## 這份文件不是什麼

這裡完全沒有講一個畫面顯示什麼、用什麼順序 —— 那是 timeline、composer 與 store 的事。它管的是已經決定好的東西怎麼被畫出來，
其他都不管。
